# !!col

- `not-found` accepts only values listed in `generateStaticParams()`.
- `blocking` waits for generation before serving a new value.
- `fallback` serves a shell while generating a new value behind `<Suspense>`.
- `dynamic` resolves the parameter at request time. Omit that parameter from `generateStaticParams()`.

### Try a first visit

the build examples. The `not-found` policy rejects it; the other policies admit it.

Use **Try again** to repeat a cold visit without clearing caches.
The suffix changes the route and query cache keys while keeping the same product.
Prefetching is disabled on these links, and each uncached query includes a 1.5-second delay.

Run `pnpm build` and `pnpm start` to compare blocking generation, fallback
streaming, and subsequent cached results. Development renders routes on demand.

### Combine policies

The mixed example sets `lang: 'not-found'` in a layout and returns
`id: 'fallback'` from the page's `unstable_generateParamMatching()` function.
`/mixed/en/2` can stream a product; `/mixed/fr/1` returns 404 because `fr` is unlisted.

The function takes no arguments. Layout policies are inherited, and a page
overrides only the parameters it specifies. Explicit policies follow URL order:
`not-found`, then `blocking`, then `fallback`, then `dynamic`.

### Keep caching and validation separate

All product queries use `use cache`, including the dynamic-parameter example.
A dynamic parameter does not prevent caching the data read with that value.

Parameter matching controls how values are admitted and generated. A
complete-route static requirement also checks the server data used by the route.
It is compatible with `not-found` and `blocking`, and still requires complete
`generateStaticParams()` results. Suspense remains necessary for work deferred
by `fallback` or `dynamic` policies.
